---
title: Time zones
description: Display events in a specific time zone, DST-correct.
---

Events lay out from their local wall-clock time. To display them in a specific
IANA zone regardless of the device, pass `Calendar` a `timeZone`. It's DST-correct
via `Intl`.

```tsx
import { Calendar } from "@super-calendar/native";

// Render every event at its New York wall-clock time.
<Calendar /* ... */ timeZone="America/New_York" events={events} />;
```

`timeZone` only changes how events display. Your `Date`s stay real instants, and
the callbacks hand them back that way:

- `onPressEvent`, `onLongPressEvent`, `onDragStart`, `onDragEvent`, and
  `onPressMore` receive the event objects you passed in, not display copies. For
  a recurring event that is the occurrence `Calendar` expanded, with its real
  `start` and `end`, as it is without a `timeZone`.
- `onDragEvent` reports the new `start` and `end` as real instants: dropping an
  event at 10:00 on a New York calendar reports 15:00 UTC in winter. An edge the
  drag didn't move keeps your event's exact `Date`.
- On the time grid, `onCreateEvent`, `onPressCell`, and `onLongPressCell` report
  real instants too.
- Callbacks that name whole days (`onPressDay`, `onSelectDrag`,
  `onPressDateHeader`, and `onPressCell` / `onCreateEvent` in the month, multiweek
  and year views) report local dates, like the `date` prop. See
  [Anchor dates are local](#anchor-dates-are-local).

## Recurring events and DST

With a `timeZone`, `Calendar` expands recurring events on that zone's wall clock,
not the device's. A daily 09:00 event in New York stays at 09:00 there after its
clocks change, on a device in any zone. See
[Recurring events](/guides/recurring-events#time-zones).

Drags follow the zone's DST changes too. A move on the time grid keeps the
event's elapsed duration, a resize sets the edge to the clock time you dragged it
to, and a time dropped into the hour a spring-forward change skips lands after
it. The drag preview is drawn on the device's clock, so on a night when the
device's own clocks change its height can be off by the offset change. The
reported `start` and `end` are not affected.

## Display copies

Render props (`renderEvent` and the per-view variants) and
`eventAccessibilityLabel` receive the display copy, whose `start` and `end` read
as the zone's wall clock, so formatting them shows the zone's time.

## All-day events

An all-day event names calendar days, not instants, so `timeZone` doesn't shift
it: a holiday on 12 November stays on 12 November in every zone. An event is
all-day when it sets `allDay: true`, or when it runs from local midnight to local
midnight without setting `allDay`. Set `allDay: false` on a midnight-to-midnight
event that should shift like a timed one.

## Outside `Calendar`

`Calendar` runs your events through `eventsInTimeZone`. Call it (or
`toZonedTime` for a single date) yourself to display zoned events in a standalone
view such as `TimeGrid`:

```tsx
import { eventsInTimeZone } from "@super-calendar/native";

const zoned = eventsInTimeZone(events, "America/New_York");
```

<Warning>
  The returned dates are for display only — they carry the zone's wall clock, not the original
  instant. Keep your source events around for editing and saving.
</Warning>

A standalone view reports what it displays. Convert in your callbacks with the
helpers `Calendar` uses:

```tsx
import { TimeGrid, fromZonedTime, zonedDragBounds, zonedEventSource } from "@super-calendar/native";

<TimeGrid
  /* ... */
  events={zoned}
  onPressEvent={(event) => open(zonedEventSource(event))}
  onDragEvent={(event, start, end) => {
    const bounds = zonedDragBounds(event, start, end, { keepDuration: true });
    save(zonedEventSource(event), bounds.start, bounds.end);
  }}
  onCreateEvent={(start, end) =>
    create(fromZonedTime(start, "America/New_York"), fromZonedTime(end, "America/New_York"))
  }
/>;
```

- `zonedEventSource(event)` returns the event a display copy was made from.
- `zonedDragBounds(event, start, end, options)` converts a dragged event's
  reported bounds to real instants. Pass `{ keepDuration: true }` for a time
  grid, so a move keeps the event's elapsed duration across a DST change. Leave
  it off for a month grid, where a drop keeps the clock time of both edges.
- `fromZonedTime(date, timeZone)` converts one wall-clock date to a real instant.

## Anchor dates are local

The controlled `date` prop, like every `Date` the calendar reads, is
interpreted in the device's local time zone: all date math runs through
date-fns (`startOfWeek`, `startOfMonth`, ...) on the local clock. Construct
anchors as local dates, not UTC instants:

```ts
new Date(2026, 7, 24); // local Aug 24, anchors the week you expect everywhere
new Date("2026-08-24T00:00:00Z"); // UTC instant, still Aug 23 west of UTC
```

On a device west of UTC, that UTC-midnight instant is still the evening of
Aug 23 locally, so a `week` view with `weekStartsOn: 1` builds the week of
Monday Aug 17, a full week before the one intended (Aug 24 is itself a
Monday). The same shift moves a `month` anchor built from
`new Date("2026-08-01T00:00:00Z")` into July.

`timeZone` doesn't change this: it shifts how events display, never how the
`date` prop is read. The dates the calendar hands back (`onChangeDate`,
`onChangeDateRange`, `onPressDay`, ...) are local dates too, so feeding them
straight back into `date` is always safe.

## Today

The day highlighted as today follows the same clock in every mode: with a
`timeZone`, it is that zone's current day, so at 22:00 UTC a calendar set to
`Asia/Tokyo` already highlights tomorrow. Pass `now` to pin it to a fixed instant.
Without either prop it is the device's current day.

The standalone views (`MonthView`, `MultiWeekView`, `YearView`, `Agenda`, and
`TimeGrid`) take the same `now` and `timeZone` props. For a headless grid, pass
the day to flag as `today`:

```tsx
import { buildMonthGrid, nowInTimeZone } from "@super-calendar/core";

const grid = buildMonthGrid(month, { today: nowInTimeZone(undefined, "Asia/Tokyo") });
```

`getIsToday(date, today)` accepts the same reference day. In `schedule` mode the
DOM and Solid `Calendar` highlight the day of the `date` prop instead of today;
the native `Calendar` highlights `activeDate` when you set it, and today
otherwise.

## The now indicator

The current-time line follows the same zone as your events: set `timeZone` on
`Calendar` and the line lands where "now" is in that zone, not where the device
clock is. Pass `now` for a fixed instant instead (a server-synced clock, or a
stable value in tests); a fixed `now` doesn't tick. `ResourceTimeline` takes the
same `showNowIndicator` / `now` / `timeZone` props and draws its line across the
lanes whenever the board's `date` is that zone's today.
